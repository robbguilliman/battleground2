# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Battleground: type two fighters, get an AI verdict on who wins (Claude) plus one pixel-art image per fighter (OpenAI image API), and save fighters to a localStorage "BattleDex". `project-brief.md` holds the scope and fixed decisions; `project-build.md` is the staged build plan. Work one stage at a time and don't start stage N+1 until stage N works. Development is local-only until Stage 7 deploys to Vercel.

**Progress:** Stages 0-5 are built (scaffold, UI shell, judge prompt, fight API with verdict and art, BattleDex, image compression). Stage 6 (the "Battleground Arcade" redesign from Claude Design project `931c42df-699b-4d52-9188-30b5c86941dc`) is built and awaiting a check with real fights, along with 6b (battle stats), 6c (8-bit sound) and 6d (the loading brawl). Stage 7 (final QA and deploy) is not started.

## Commands

- `npm install`: installs `@anthropic-ai/sdk`, `openai` and `zod`, used by `api/`.
- `npm run dev:vercel`: `vercel dev`, the way to run the app locally now that `api/fight.js` exists. Keys go in `.env` (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`).
- `npm run dev`: zero-dependency static server (`dev-server.js`) at http://localhost:3000. It only serves files, so the Fight button gets a 404 from `/api/fight`.

There's no build step, linter or test suite. Vercel serves the repo root as static files (`vercel.json`: no framework, `outputDirectory: "."`). `.vercelignore` keeps `*.md`, `dev-server.js` and `.env*` out of deploys.

## Architecture

**Frontend:** vanilla JS, no framework or bundler, two pages sharing `style.css`. `index.html` + `script.js` is the fight page. `battledex.html` + `battledex.js` is the BattleDex. `dex-store.js` holds the storage helpers and is loaded by both. `index.html` holds four `<section class="view">` elements (`view-form`, `view-loading`, `view-result`, `view-error`). `showView(name)` sets `hidden` on every view except the named one, so exactly one is ever visible. Keep this pattern for new views. Fighter cards are `card-a`/`card-b`; the winner card gets `.is-winner` (gold glow, WINNER tag, light rays) and the loser `.is-loser` (grayscale plus K.O. stamp). The HP bars (`hp-a`/`hp-b`) get the same two classes, and the winner's remaining HP comes from its odds (`winnerHp()`): a blowout leaves it nearly full, an upset barely alive. Each card has a stat panel (`#stats-a`/`-b`: Battle Value, five 0-100 bars, strengths and weaknesses), and the verdict column shows the odds bar plus an UPSET badge when the underdog won. Results saved before battle stats existed simply hide these. `requestFight()` POSTs to `/api/fight` with a 120s abort timeout and turns every whole-fight failure (offline, timeout, 400, 429, verdict error) into a `FightError` with its own title and message for the error view. Image failures don't use the error view: `renderResult()` shows a placeholder SVG on that card plus a note (`#art-error-a`/`-b`), styled differently for `image_blocked`.

**BattleDex:** saved fighters live in `localStorage` under `battleground.battledex` as an array of `{ id, label, image, sourceKey, stats, wins, losses }`. `stats` is the fighter's battle stats from the fight it was saved after (missing on fighters saved before battle stats existed, then filled in by their next picked fight). The win/loss record starts with that fight and grows each time the fighter is picked for a fight (`recordFightResult()` in `dex-store.js`, called only from the submit handler so a re-shown `#last-fight` never counts twice). Cards show `BV` and the record. On save, `compressImage()` (in `dex-store.js`) redraws the art on an off-screen canvas at 512px and re-exports it as WebP at quality 0.8, or JPEG where WebP encoding isn't supported. That's about 30-65K characters per fighter instead of about 200K, so roughly 100 fighters fit in the quota. `sourceKey` is a fingerprint of the full-size original (`imageKey()`), so the result view can still tell a fighter is already saved. `battledex.html` compresses any entry over 120K characters once (fighters saved before Stage 5). If compression fails, the original is saved instead. Save buttons are on the result view (`script.js`). Viewing, removing and clearing happen on `battledex.html`. Every storage read and write is wrapped in try/catch, and a full quota shows a message instead of throwing. Cards are built with `textContent`, never `innerHTML`. The card itself isn't clickable; its controls are Pick and remove.

**Picking saved fighters:** on `battledex.html`, up to two cards can be picked. "Fight with picked" writes them to `sessionStorage` (`battleground.picks`) and opens `index.html#picked`, which reads them once (`{ id, label, image, stats }`), fills the form and shows a "From your BattleDex" badge. On submit, picked sides whose name is unchanged are sent as `reuseArt: ["A"|"B"]`, plus their saved stats as `knownStats`, so a saved fighter keeps the same Battle Value every fight. The API skips image generation for those sides and returns `{ reused: true }`, and the client puts the saved image back in. Editing a picked name drops the pick.

**Last fight across pages:** each result is also written to `sessionStorage` (`battleground.lastFight`, as `{ fighterA, fighterB, verdict }`), so it lasts for the tab, survives a reload and is gone in a new tab. "Back to last fight" on `battledex.html` links to `index.html#last-fight`, which re-renders that result and then clears the hash. A fighter already in the BattleDex shows "Saved ✓", matched by `sourceKey` or by image.

**Backend** (`api/`): Vercel Node serverless functions, written in CommonJS (`require`/`module.exports`, since `package.json` has no `"type": "module"`). Shared code goes in `api/_lib/`, because Vercel doesn't turn underscore folders into routes.

**Judge prompt** (`api/_lib/judge-prompt.js`):
- Exports `JUDGE_SYSTEM_PROMPT` and `buildJudgeUserMessage(fighterA, fighterB, knownStats)`. The helper wraps each fighter in `<fighter_a>`/`<fighter_b>` tags, saved stats in `<fighter_a_stats>`/`<fighter_b_stats>`, and strips all four tags from user text, so a fighter can't break out of its own tag.
- The judge rates both fighters realistically on a shared 0-10,000 Battle Value scale (anchors in the prompt: snail 1, adult human 100, nuclear bomb 7,000, Doctor Strange 9,000), counts group size realistically unless one side is untouchable or can wipe out a crowd at once, and names a favorite with a win chance that is never 0% or 100%. It writes 3-5 playful sentences for each possible winner (the upset one as a fluke scaled to the odds), treats fighter text as data only, and never leaves the judge role.
- It deliberately has **no output-format or JSON instructions**. The verdict shape is defined only by `StatsSchema`/`VerdictSchema` in `api/fight.js`, with field meanings in `.describe()`: `fighterA`/`fighterB` (stats), `favorite: z.enum(["A", "B"])`, `favoriteWinChance`, `reasoningIfAWins`, `reasoningIfBWins`. Sides are A/B rather than names so "cow" vs "cow" still tells the UI which card won. No `.int()` or min/max in the schema (they leak noise into the JSON schema); the server rounds and clamps instead. Don't add format instructions back to the prompt.

**`api/fight.js`:** `POST { fighterA, fighterB, reuseArt?, knownStats? }` returns `{ winner: "A" | "B", reasoning, upset, odds: { A, B }, stats: { A, B }, images: { A, B } }`. `odds` are win chances in percent; the server rolls the winner from them (`rollWinner()`, favorite capped at 99.9999999999%, so a trillion-to-one upset can happen) and returns the matching reasoning. `knownStats` is honored only for `reuseArt` sides and only if it passes `StatsSchema`; those sides get their saved stats back unchanged. Each image is where each image is `{ src }` (a JPEG data URI), `{ error: { type: "image_blocked" | "image_failed", message } }`, or `{ reused: true }` for a side listed in `reuseArt`. Whole-fight failures return `{ error: { type, message } }`. In order:
1. The per-IP rate limit: 5 requests/minute, sliding window, 429 with `Retry-After`. It's an in-memory `Map` (`createRateLimiter()` in `api/_lib/rate-limit.js`), so it's exact under `vercel dev` but only per-instance on Vercel.
2. Input validation: both fighters required, max 50 characters each. The same limit is the inputs' `maxlength` and `MAX_FIGHTER_LENGTH` in both `script.js` and `api/fight.js`; keep all three in sync.
3. The verdict and both images run in parallel. The verdict uses `client.beta.messages.parse` on `claude-sonnet-5-5`, effort `medium` (realistic stats need some thought; it runs alongside the slower image generation), `output_config.format: betaZodOutputFormat(VerdictSchema)`, and server-side refusal fallbacks (`fallbacks: "default"`). Anthropic's own 429 is reported as a 503 so the UI never confuses it with ours.
4. A failed verdict fails the whole fight and aborts the image requests. A failed image only fails its own side.

`vercel.json` gives `api/fight.js` a `maxDuration` of 120s. A fight takes about 15-20s, mostly image generation.

**Fighter looks** (`api/_lib/fighter-looks.js`): `describeFighters()` makes one extra Claude call per fight (`claude-sonnet-5-5`, effort `low`, zod-structured `{ fighterA, fighterB }`). It writes a 40-80 word appearance description of each fighter, with book characters described as the source text describes them. It runs in parallel with the verdict, and both images wait for it. It resolves to `null` on any failure, and the art then falls back to the name alone. `pickPoses()` picks two different random poses from `POSES`, with A facing right and B facing left. Sides in `reuseArt` skip both steps.

**Fighter art** (`api/_lib/fighter-art.js`): the image prompt is the fighter name, then the description, then the pose, then the group rule, then the style template. `gpt-image-2.5-flare`, 1024x1024, quality `medium`, JPEG at compression 80 (about 150-200 KB each, keeping the response under Vercel's 4.5 MB limit). `maxRetries: 0`, so a failure doesn't double the wait. `gpt-image-1` was shut down in October 2026, and Flare rejects the `complexity` param. OpenAI's `moderation_blocked` error code becomes `image_blocked`; everything else becomes `image_failed`.

**Image rules:**
- A group input like "10 cows" still gets exactly one image for its side. Handle that in the image prompt, not by looping.
- Every image prompt ends with the shared art style template (16-bit pixel art, retro sprite style, plain solid color background, no text), quoted verbatim in `project-build.md` Stage 3.
- Moderation-blocked is its own error type and UI message, separate from a generic image failure.

**Look (Stage 6):** a dark arcade style with design tokens on `:root` in `style.css`: `--ink`, `--panel`, `--gold`, `--red`, `--blue` (P1 is blue, P2 is red) and so on. Three Google Fonts: Bungee (display), Press Start 2P (pixel labels) and Chakra Petch (body). Each view is a full-height `.view` holding a `.wrap`; the grid floor and the `body::after` scanlines are decorative. `prefers-reduced-motion` turns every animation off. For a 429, the error view runs a countdown from `Retry-After` (`startCountdown()` in `script.js`) that keeps Try again locked until it reaches zero.

**Sound** (`sound.js`, loaded first on both pages): 8-bit music and effects synthesized live with the Web Audio API (pulse, triangle and noise voices), so there are no audio files and no API calls. `window.Sound` has `music(name)` (loops `title`, `loading`, `result`), `fanfare(upset)` (one-shot, then the result loop), `jingle("error")` and `sfx(name)`. `showView()` picks each screen's music; a fresh result gets the fanfare from the submit handler, a re-shown `#last-fight` goes straight to the result loop. The BattleDex plays the title loop, blips when you move to a different card (hover, focus or arrow keys) and has pick/unpick/remove sounds. The loading brawl uses `whoosh`, `hit`, `smash`, `clang`, `whiff`, `charge`, `blast` and `ko`; all but `ko` play at a slightly random pitch each time. Songs are `note:steps` strings (a step is a 16th note) and every track in a song must add up to the same number of steps. All music is original; keep it that way. Browsers only allow audio after a click or key press, so music waits for one. Sound is on by default; the `[data-sound-toggle]` button stores the choice in `localStorage` (`battleground.sound`). Audio is suspended while the tab is hidden.

**Voice:** all user-facing copy, errors included, uses a playful arena-announcer voice ("Empty corner!", "Whoa, easy, champ!"), but every message still says what went wrong and what to do next. Error text comes from the API (`api/fight.js`, `fighter-art.js`), with client fallbacks in `requestFight()`. The loading quips are `LOADING_MESSAGES` in `script.js`. They're `aria-hidden` and rotate as a shuffled deck while the loading view is shown.

**Loading brawl** (`brawl.js`, loaded before `script.js`): while a fight loads, the two loading cards (`#brawler-a`/`-b`) trade blows. `window.Brawl` has `start()` and `stop()`, called only from `showView()`, so it runs exactly while the loading view is up and `stop()` clears every timer, animation and effect at once. Each beat is a lunge plus a hit, a big hit, a block or a dodge, or now and then a special move (the attacker charges with a strobing glow, then fires an energy ball that can still be blocked). Every landed blow gets a hit-stop (a short freeze, longer for heavier blows), and heavy ones a camera punch (arena shake plus zoom) and a white flash. Consecutive hits by one side show a combo counter. The HP bars are driven by `--hp`/`--ghost` custom properties: the white ghost bar trails each hit and drains a moment later. Card motion uses the Web Animations API on `.brawler` (the inner wrapper; `.mystery` keeps the CSS idle bob); one-off effects (`.fx-burst`, `.fx-spark`, `.fx-dmg`, `.fx-combo`, `.fx-shield`, `.fx-orb`, `.fx-flash`) are spawned into `#brawl-fx` and remove themselves. `data-damage` on each side (0/1/2) shows the cracks. The warm-up must never hint at the real winner: whoever is ahead usually takes the next hit, nobody drops below 4 HP, and when either side falls under 22 both refill and the round number goes up. Only once the verdict is in does the submit handler call `await Brawl.finish("a" | "b")`: the real winner lands a K.O. blow (about 1.1s) before `renderResult()`. It resolves at once if the brawl isn't running, and `stop()` resolves it too. Live commentary with the fighters' names ("A GRIZZLY BEAR connects!") pops into its own banner (`#brawl-call`) under the round title; big moments always get a line, ordinary ones at most every 1.8s. The quips stay in the bottom line. The submit handler puts a picked fighter's saved art on its loading card (`setLoadingArt()`). With `prefers-reduced-motion` the loop doesn't start. It's all `aria-hidden`.

**Secrets:** API keys live only in env vars, never in client code. Locally they go in `.env` (git-ignored by `.env*`; `.env.local` holds only the Vercel CLI token). On Vercel, set them as project env vars.
